# Security

Ravenshelf is a preview application. Its link checks, popup restrictions and transfer validation do not certify a website, archive or installer as safe. Downloaded files never run automatically.

## Reporting a vulnerability

Please avoid publishing exploitable vulnerability details in a public issue. Use **Security → Report a vulnerability** in this repository to send a private report to the maintainer. If that option is unavailable, open a brief issue asking for a private reporting channel, without the exploit, private links or sensitive data. No dedicated security email or response-time guarantee is currently published.

Include the Ravenshelf version, affected component, impact, and a minimal reproduction using fictional data once a private channel is available. Do not send credentials, cookies, payment information, game archives or your complete application profile. Focus reports on the latest published version.

## Data to keep private

Ravenshelf's local profile can contain download URLs, request headers, cookies, installed-game paths and saved collections. Saved download headers and the host browser's cookie store use Windows-account encryption. From 0.3.1, unavailable or failed header encryption never falls back to plaintext: headers stay in memory, are omitted from the saved queue, and require link refresh after restart. Older plaintext queue headers are removed from the current saved file; existing backups are not rewritten. The profile should still be treated as private. Do not upload profile folders, `library.json`, `installed-games.json`, browser storage, `.atlas-part` files or `.atlas-segments-*` folders to GitHub.

Redact usernames and personal paths from logs or screenshots. Signed direct-download URLs can grant temporary access and should be treated as private.

## Project boundaries

- Releases are built on GitHub-hosted Windows machines from reviewed source, with a matching release tag, after the test suite passes. They carry a SHA-256 checksum and a signed build-provenance attestation; see [the restricted verification command](docs/SUPPLY-CHAIN.md#verify-the-published-executables-build-origin).
- The executable disables Electron's run-as-Node mode, `NODE_OPTIONS`, debugger flags and extra `file://` privileges. From 0.3.1, archive-only application loading is paired with embedded ASAR-integrity validation. `npm run verify:build` inspects the actual packaged fuse values. The executable remains unsigned; these settings are not a publisher-authenticity guarantee.
- Finished downloads can be scanned with Microsoft Defender. A successful process exit alone is not labeled clean: recognized explicit clean output is required, and ambiguous output needs review. Threat or remediation evidence takes precedence. Ravenshelf does not change antivirus settings; no scan result certifies a file as harmless.
- CodeQL security-and-quality analysis, locked-dependency audits and Dependabot dependency updates run on the repository. Test and build jobs also verify npm registry signatures and available package provenance. A successful scan workflow does not mean its alert list is empty, and not every dependency provides a publisher provenance attestation.
- Prospective source checks require GitHub-verified signatures on checked PR commits and the exact source selected for hosted preview/release builds. GPG, SSH, S/MIME and supported GitHub platform signatures are accepted; this is not a claim that every historical commit was signed. Existing unsigned history is retained, and private signing keys are not stored in CI. See [the source-verification policy](docs/SUPPLY-CHAIN.md), including the proposed hosted ruleset rollout.
- Public release builds require successful Test, CodeQL and Source integrity push runs for the exact source commit. Builders have read-only repository permission. A separate attestation job only downloads and attests the tested artifact; it does not check out source or run dependency/build code. Publication verifies the artifact's cryptographic attestation against the repository, expected workflow, exact source/workflow commit and GitHub-hosted runner policy. From 0.4.2, a separate read-only job also checks the exported build record with the in-app updater's own verifier before the record is published beside the executable; a record that installed copies would refuse stops publication. Preview builds exercise the same attestation chain without publishing a release.

- The main application page uses an isolated preload bridge with a limited set of operations. Remote host and gameplay windows do not receive that bridge.
- File and cover-image requests enforce HTTPS and public-network checks. Cover images use a bounded raster-only loader without browser-session credentials. Supported-host windows restrict navigation, popups and requests, but they are not an antivirus or a universal ad blocker.
- Byte ranges and file-version validators help prevent incorrect resumptions and mixed file sections. This is separate from scanning archive contents or checking publisher-provided hashes.
- Installed-game detection reads local metadata; it does not launch discovered executables.
- From 0.4.2, automatic update checks only look for a newer release and announce it. Nothing is downloaded or installed until you choose **Download and install**; an update is applied only after that choice, on close or with **Restart now**.
- Before downloading an approved update, Ravenshelf verifies the release's signed build record (a Sigstore bundle published as `Ravenshelf-<version>-Windows.exe.sigstore.json`). The check covers the Fulcio certificate chain and its certificate-transparency proof, the Rekor transparency-log inclusion proof, and the DSSE signature over a SLSA provenance statement that names the exact executable and SHA-256. The signer must be `publish-release.yml` on `refs/heads/main` in this repository, issued by GitHub Actions, on a GitHub-hosted runner, with this repository's and owner's numeric IDs. Sigstore's trusted root is refreshed through TUF, with the copy bundled in the app as a fallback. Any failure stops the update.
- The executable must also match the size and SHA-256 in GitHub's asset metadata and the release checksum file, and the staged candidate is checked again before installation. Update requests are limited to this repository's release list and exact release download paths, with restricted redirects. These checks establish that the file was built by the release workflow from this repository's `main` branch; they are not a Windows publisher signature, and compromise of the repository, its workflow or its maintainer account remains a trust risk. A renamed, deleted and re-created, or transferred repository stops in-app updates until a manually installed version trusts the new identity.
- After a finished update, Ravenshelf removes the staged copy, helper copy and job files, and the previous executable kept next to the app, only when the update's own result shows success and that rollback copy matches the replaced executable byte for byte. Links, unexpected files, failed updates and profile backups are left alone.
- A native Windows helper waits for app exit before replacing the portable executable, checks file identity/digests and uses a backup for replacement recovery. Critical profile files are backed up first. It does not change PowerShell policy, request elevation, disable protections or terminate another application. This is not protection against all malicious software running as the same Windows user.
- The helper intentionally uses three Windows APIs (`CreateFile`, `GetFileInformationByHandle`, `GetFileType`) through `SafeFileHandle`. They allow file-identity/hard-link checks, rejection of reparse points and locks against replacement while verifying bytes. DLL lookup is restricted to Windows System32. CodeQL's general native-code declarations/calls notes apply to this necessary boundary; they are not suppressed, and do not by themselves identify an exploitable flaw. The signatures, ownership/disposal and failure paths are reviewed and exercised with disposable updater fixtures, including real Windows short paths, hard links, junctions, changed bytes and locked files.
- Queue cleanup defaults to removing entries while keeping files. File deletion requires a fresh preview and explicit confirmation, validates managed file identities, and reports partial failures. Its byte totals are logical estimates, not a guarantee of freed disk space.
- Archive-set checks inspect recognized filename numbering and known sizes. They cannot infer an unknown final part or establish archive completeness. Manually selected SFV/MD5/SHA-256 checks run in a bounded worker and compare local files to that manifest; a match is not evidence of authenticity or harmlessness.
- The optional browser extension (0.5.0) requests no host permissions (`host_permissions`). It uses the browser's downloads, declarative blocking, navigation-event, menu, notification and native-messaging interfaces; its pages load only packaged scripts under a strict content policy, and it makes no network requests itself. It has three page scripts. From 0.6.0 one runs in the top frame of www.youtube.com to add the player button: it builds its controls without HTML injection, acts only on trusted user clicks, and sends the page address to the extension, which accepts it only from that script in a YouTube top frame. From 0.7.0 one runs in the top frame of www.nexusmods.com and only reads which game, mod and file a mod's page shows: it changes nothing on the page, makes no requests, does nothing in private windows, and reports only to the extension, which accepts the report only from that script in a www.nexusmods.com top frame and cleans it. The label, built from those reports or from the address of the page that started the download, is attached only to a download fetched from Nexus Mods' file servers (`nexus-cdn.com`) that began there or on www.nexusmods.com. The app checks every field of it again and keeps it only for such a file. A label decides: the folder inside `Mods` and text on screen; one connection; that the link is never looked up again and may be redirected only among those file servers; that the file is known by its path there and its name, not by its signed query; that a failed or cancelled entry takes a new link only from a later download of the same file; that the signed query and the page address sent with the request are dropped when the file finishes or is cancelled; that a refused link shows a fixed sentence; and that **Delete files** may remove a file of any type, only from `Mods\<game>`. The **Mods** page opens a mod's page in the user's browser at an address built only from the checked game and mod number. From 0.10.0 one runs in the top frame of fitgirl-repacks.site: it acts only on a trusted left click without modifier keys on a magnet link, and sends only that link (at most 8,192 characters) to the extension, which accepts it only from that script in a fitgirl-repacks.site top frame, never from a private window and only while its switch is on; in every other case the browser opens the link itself. It is loaded unpacked or as a temporary add-on, not from a browser store, so it receives no store review.
- YouTube downloads (0.6.0) need a one-time setup the user starts. yt-dlp, Deno and FFmpeg come only from their publishers' GitHub releases at fixed versions, through GitHub's download hosts; the archives and each extracted program must match the sizes and SHA-256 values recorded in the source, and the programs are hashed again before their first use in each session. Ravenshelf passes yt-dlp the canonical address of one video after `--`, with configuration files, plugins, cookies and remote components switched off, the checked Deno as its only JavaScript runtime, no shell, a minimal environment and a private temporary folder. Its output is read for progress and turned into fixed messages. Finished files are published without overwriting anything and keep the internet-zone mark. New pinned versions arrive only with a Ravenshelf release; the programs never update themselves.
- Torrent downloads (0.10.0) are off until the user accepts what torrents share, and their engine, aria2 1.37.0, is set up only when the user chooses: its zip comes from aria2's GitHub release through GitHub's download hosts and must match the size and SHA-256 recorded in the source (the release publishes no checksums; the value matches Scoop's and winget's records), and only `aria2c.exe`, with its own recorded size and SHA-256, is extracted. aria2 runs with a frozen argument list (no configuration or `.netrc` file, no log, no local peer discovery, IPv4 only, no following of links in torrents, no overwriting or renaming, uploading only up to a positive limit and stopped at the end unless the user chose to share for up to 15 or 60 minutes; stopping a torrent while it shares removes it from aria2, or stops aria2 if that takes more than a few seconds, before its files are published), a minimal environment, no shell and no console, and exits with Ravenshelf. Its JSON-RPC listens only on 127.0.0.1 with a 64-character random secret for each start and no allowed web origins; its replies are size-capped and treated as untrusted, and only its error numbers are mapped to fixed messages. Magnet links keep only an info-hash, a cleaned name (format characters removed) and at most 30 `udp`/`http`/`https` trackers without credentials, none written as loopback, private or link-local addresses (read the way a web address is, so `127.1` counts) or local names; current tracker DNS answers are checked before use, and unresolved, private or mixed answers are dropped. aria2 performs later DNS lookups, tracker redirects and peer connections independently, so this preflight does not enforce socket-level isolation or a VPN kill switch. Returned and cached metadata are rebuilt around the exact verified info dictionary using only the reviewed magnet trackers; injected trackers, web seeds and other top-level fields are discarded. aria2's DHT file, which holds its node ID, is deleted before each start and after aria2 exits. A torrent's file list must hash to the magnet's info-hash and pass a strict bencode reader; names Windows can't store exactly as written, names with Unicode format characters (other than the zero-width joiner and non-joiner Arabic-script languages need), names the browser-download checks block as disguised, `~<digit>` short-name look-alikes, duplicates that differ only in (upper) case, file/folder clashes, more than 10,000 files, paths too long for the download folder and version 2 torrents are refused, never renamed. The user chooses the files; aria2's own file list must equal the checked one before it starts. Files download into a private working folder and are published only when every chosen file has its exact size, without replacing anything, each with the internet-zone mark, and the result is scanned by Defender (as a folder; a folder that is itself a link is not scanned). Torrents expose the PC's IP address to everyone sharing the same torrent; Ravenshelf says so before they can be turned on and does not hide it. aria2 1.37.0 is aria2's newest release and has a known, unfixed certificate-check weakness (CVE-2026-8367: it does not check that a server certificate was issued for servers). Ravenshelf uses aria2 only for torrents, never for web downloads or updates; its only HTTPS connections go to HTTPS trackers named in a magnet link. Someone who controls your network and holds such a certificate could pose as such a tracker, which would let them see which torrent you are getting (as plain trackers and the people sharing it can anyway) or give aria2 wrong lists of people; every piece is still checked against the torrent, so the files cannot be changed that way.
- Hosts that have shut down (ZippyShare, BayFiles, LetsUpload; their names can change hands) are refused by the app's network layer for every request and redirect. PixelDrain and MultiUpload addresses are rebuilt from validated IDs on fixed domains, responses are size-capped, and PixelDrain's own virus flag is reported, not offered.
- **PC specs** (0.7.0) runs a fixed, read-only script with Windows PowerShell from `System32`: no profile, no input, a hidden window, a 20-second limit, at most 512 KB of output, and PowerShell's module path set to the module folder inside Windows' own folder. The answer is treated as untrusted text and kept in memory only. A test holds the script to fixed lists of commands, classes, properties and registry paths.
- In Arabic (0.8.0), names, paths and addresses inside translated text are kept apart with Unicode isolates, so they cannot change the direction of the sentence around them. The window's language data is written by the main process as JSON; only plain texts are taken from the bundled Arabic file.
- The connector `ravenshelf-browser-host.exe` is compiled from `src/browser-host.cs` like the update helper and checked against its build record (size, SHA-256 and executable header) before it is copied into the profile and registered for the current user only (`HKCU`). Browsers start it only for Ravenshelf's own extension (pinned Chromium ID and Firefox ID). It relays one message to the app over a named pipe whose name and 64-character token are random for each app session; the app checks the token in constant time, the extension origin, the exact message shape and size limits, and a request rate limit.
- Before a browser handoff is downloaded, the app inspects the link without browser cookies, following redirects one hop at a time and never contacting listed, private-network or unencrypted destinations, then compares the file name with the first 4 KB. Disguised programs, unencrypted programs and listed sites are blocked and cannot be forced; programs, scripts and disk images need explicit confirmation. Files taken over this way keep the internet-zone mark.
- Site blocking uses the browser's `declarativeNetRequest` engine with rules built from public lists. Lists are size-bounded, syntax-checked and rejected when an update shrinks suspiciously; entries for infrastructure Ravenshelf needs (GitHub, Sigstore, VirusTotal, list mirrors) and the supported file hosts are never blocked. The file-host guard blocks only navigations that FuckingFast and FileKeeper pages start toward other sites.
- VirusTotal is opt-in with the user's own key. Only domain names and SHA-256 fingerprints are looked up, the key travels in a request header to `www.virustotal.com` only, and it is sealed with Windows protected storage and never returned to the window.
- The connector turns every failure into one of a few fixed replies (`invalid`, `not-running`, `timeout`, `failed`) and never prints exception text, so it deliberately catches all exceptions at those points. CodeQL's general notes about catch-all clauses there are reviewed and kept, as for the update helper.
- Malware already running as your Windows user could alter the profile, the extension folder or the registry entries; that is the same boundary as for the app itself.
- Copied-link recognition is opt-in and local. It never queues downloads or contacts a host until the user continues through link checking. Game requirements and recommendation counts are rendered as text; review stars are a conversion of Steam's positive-review ratio, not generated opinions.
- Close/shutdown completion actions are opt-in for the current session and use a cancellable countdown. Requested scans must finish cleanly; queued/running scans delay the action, while adverse or uncertain results block it. Readiness is checked again immediately before executing the action. Turning off future automatic scans does not waive an already recorded scan result.

A release checksum checks agreement with the published file. A valid build attestation records build provenance, not the safety of the code or downloaded games. Neither substitutes for an executable publisher signature.

Updaters in 0.4.1 and earlier do not verify the build record; 0.4.2 and later do. Anyone can also verify a release separately, restricting the expected repository, release workflow, reviewed source commit and runner type; see [the verification command](docs/SUPPLY-CHAIN.md#verify-the-published-executables-build-origin). GitHub documents the asset `digest` field in its [release asset API](https://docs.github.com/en/rest/releases/assets?apiVersion=2022-11-28).

Ravenshelf has no built-in proxy/VPN enforcement or kill switch. Interface binding alone would not make both browser and download traffic leakproof. Search API integration, including Brave, is deferred and is not an anonymity or free-service guarantee.

Dependency updates and regression tests are part of maintenance, not a guarantee that all vulnerabilities have been found. See [the architecture notes](docs/ARCHITECTURE.md) for implementation boundaries and [the privacy guide](docs/PRIVACY.md) for local data and network visibility.
